## How to use this doc, every session

1. Re-read `CONTEXT.md` and `FUTURE.md` first — both may have been updated by a prior session per step 6 below. Confirm the session you're about to start is actually still the next unchecked one; sequencing across epics matters (see `FUTURE.md`'s "Sequencing — decided").
2. Read this session's section in full before writing code. Each one names the files it touches and the specific vendor CSVs or existing patterns to verify against — don't skip the verification steps for a shortcut. Every hardcoded assumption about a NERIS field in this repo's history so far came from skipping exactly this (`CONTEXT.md`'s "Field-verification discipline").
3. Implement the session's scope only. If you discover adjacent work that seems necessary, note it in this file under that session's "Discovered during implementation" line (add the heading if it's the first note) rather than doing it — a future session picks it up.
4. Add or update the test automation named in the session's "Tests" subsection as you go, not as an afterthought — per this repo's actual convention (`TESTING.md`): fast Vitest for pure functions/schemas/mocked server actions, `*.db.test.ts` (Testcontainers) for real-DB behavior (constraints, races, cross-tenant isolation), Playwright E2E only where the session explicitly calls it out. Run the fast suite (`npm run test`) before ending the session; run `npm run test:db` too if the session touched schema, migrations, or DB-direct logic. A full combined run (`npm run test`, `npm run test:db`, `npx tsc --noEmit`, `npm run lint`) only needs to happen at Session 17, not every session — targeted runs are fine while working through 1–16.
5. Stop for manual browser verification per `CLAUDE.md`'s Stop-after-each-section rule before declaring the session done. State plainly what you actually clicked through versus what you're inferring from code/tests — those are different claims.
6. At the end of the session, update the doc(s) named in that session's "Docs to update" line, then stop and let the human commit. Do not commit yourself.

**Findings:**

- **Three of the seven "unwired" modules have no data-entry surface at all — not wired, on purpose.** `riskReduction`, `emergingHazard`, and `tacticTimestamps` each have a real Prisma model (`IncidentRiskReduction`, `IncidentEmergingHazard`, `IncidentTacticTimestamps`) but zero `lib/validation/` schema, zero `app/incidents/[id]/...` route, and aren't even fetched by `get-incident-detail.ts`'s Prisma `include`. `tacticTimestamps` genuinely does have real `neris_core=TRUE` fields (contradicting this session's own "may legitimately have none" aside) — `time_command_established`/`time_sizeup_completed`/`time_suppression_complete`/`time_primary_search_begin`/`time_primary_search_complete`/`time_extrication_complete` unconditionally, plus `time_water_on_fire`/`time_fire_under_control`/`time_fire_knocked_down` for FIRE incidents — gated at the module level by `core_mod_incident.csv`'s `tactic_timestamps` row (`neris_core_if="final incident type includes fire"`, matching the existing code comment). But wiring a hard-blocking required-schema for a module nobody can fill in would permanently brick Submit for every FIRE incident — worse than the gap it would "fix." **Not wired.** Building the data-entry UI/schema for these three is prerequisite work for a future session, not this one.
- **`exposure`'s container-level cardinality is genuinely ambiguous, and the safe reading was chosen.** `core_mod_incident.csv`'s `exposure` row is `neris_core=TRUE` with a *blank* `neris_core_if` — unlike `rescue_ff`/`rescue_nonff`/`emerging_hazard`, which are explicitly self-referential-conditional (`"casualty_rescue_int_ff > 0"`, `"eh was involved"`). Read literally, blank `neris_core_if` could mean "unconditionally required," which would mean every incident needs at least one exposure row — operationally absurd (most incidents have zero exposures) and a real risk of bricking routine Submits if wrong. Implemented as **per-row validation only, no cardinality (`min`) requirement** — the safe reading given the ambiguity. Flagging for a product decision rather than guessing in the "hard block everything" direction.
- **Two real tab-schema bugs found and fixed while building the Rescue required-schemas** (same "wrong currently-required flag" shape as Session 1's dispatch fix, just newly discovered because this module had never been examined against the CSV before): `incidentRescueNonFfSchema.rescueType` was `.optional()` despite `nonff_rescue_type` being `neris_core=TRUE` unconditionally in `mod_rescue_nonff.csv`; `casualtyType` was `.optional()` on **both** `incidentRescueFfSchema` and `incidentRescueNonFfSchema` despite `ff_casualty_type`/`nonff_casualty_casualty_type` both being `neris_core=TRUE` unconditionally. Both are now required. De-risked by `TypeCasualty` having an always-answerable `UNINJURED` value and `TypeRescue` having `NO_RESCUE_NEEDED` — nobody is forced into a false positive. Both fields already had real form inputs in `rescue-ff-form.tsx`/`rescue-nonff-form.tsx`, so this doesn't break "can't fill it in."
- **`mod_exposure.csv`'s `exposure_displaced_cause` conditional (required when `displaced_number > 0`) wasn't enforced anywhere — fixed.** Added a `superRefine` to `incidentExposureSchema` alongside the existing `exposureItem`-conditional, same pattern, same file.
- **`Unit Response` cardinality implemented with confidence, unlike Exposures**: `core_mod_dispatch.csv`'s `dispatch_unit_response` is `neris_core_app=TRUE` unconditionally (Session 1's finding — `neris_core_app` is the correct signal for this specific field since it's a Dispatch-module row), and "every real incident has at least one responding unit" is unambiguous common sense, unlike Exposures. `incidentUnitResponseRequiredSchema` requires `min(1)`.
- **Prisma-null vs. Zod-`optional()`-undefined mismatch, handled.** Repeatable child rows come back from Prisma with `null` on absent optional columns; Zod's `.optional()` rejects `null` (only `undefined`). Added a small `stripNulls()` helper in `get-submit-completeness.ts` so reused tab schemas validate real DB rows correctly instead of false-positiving on every legitimately-empty optional field.
- **Every `.db.test.ts` fixture that builds a dispatch record via `updateDispatch` was already stale from Session 1**, independent of this session's changes — they all still set the three old `dispatchTimeCall*` fields and never set `timeIncidentClear`, so they built incomplete-per-the-real-gate incidents. Not caught in Session 1 since `npm run test:db` needs Docker, which wasn't available there. First pass at fixing this session only caught `concurrent-writes.db.test.ts`; running `npm run test:db` against real Docker (once available) caught the same staleness still present in `incident-journey.db.test.ts` (both the main journey test and `runCoreOnlyJourney`) — three tests failing with `'OPEN'` instead of `'SUBMITTED'`. Root-caused via a throwaway debug test dumping `getIncidentDetail`/`getSubmitCompleteness` output directly, rather than guessing. All four `dispatchFd` blocks across both files now set `timeIncidentClear`. **Verified: `npm run test:db` — 36/36 pass; `npm run test` — 346/346 pass.**

**Discovered during implementation — deferred, not fixed this session:**

- **Address decomposition remains a known, pre-existing, already-documented gap — not newly discovered, but now concretely load-bearing.** `CONTEXT.md`'s Data model rationale already says NERIS's 38-field civic-location decomposition is "intended to be computed by geocoding at submission time... Not built yet." `mapLocation()` puts the app's single `streetAddressComplete` string into `LocationPayload.street` (the closest available field) and best-guesses `city` → `incorporated_municipality` (one of four NERIS community-type buckets, unconfirmed which applies without geocoding) rather than leaving location data out of the payload entirely. `LocationPayload` itself has zero required fields, so this doesn't block a 201 — but it's a real, likely source of `/validate` rejections once Session 16 runs, tracked there rather than solved here (geocoding is out of this session's scope).
- **`IncidentRescueFf.linkedUnitId`/`reportedUnitId` were never migrated to the real `Unit` FK the way `IncidentUnitResponse.unitIdLinked` was in Session 4** — confirmed by reading the Prisma model directly rather than assuming Session 4 covered every unit-reference field. `linkedUnitId` is a plain, non-FK `String`, which the vendor CSV's own `format: See unit.neris_id` comment implies is meant to hold a real NERIS unit ID directly (unlike `IncidentUnitResponse`'s pre-Session-4 free-text field, which held a local unit label). Mapped as-is (`unit_neris_id: r.linkedUnitId`) since that's what the field is for, but this is worth a future look — a real FK here (or at least reusing the `Unit` picker UI) would remove the "hope the firefighter typed a valid NERIS ID" risk this field currently carries.
- **`FfInjuryDetailsPayload.unit_neris_id`/`job_classification`/`unit_continuity` sub-fields are not fully wired** — `job_classification` maps from `casualtyClassification` (confirmed via the vendor YAML's `map_orm_landing: casualty_sub_injury_ff.type_job_classification`), but `unit_continuity` has no backing field in `IncidentRescueFf` at all and is simply never sent (it's optional, so this is safe, just incomplete). Noted rather than silently dropped.

**Findings:**

- **`attemptNerisSubmission` (`lib/neris/submit-incident-to-neris.ts`) is one shared function for all three trigger paths**, not three separate implementations — `approveIncident`, `resendNerisSubmission`, and the sweep route all call the exact same code, differing only in `trigger`/`actorId`/which incident they pass in. It builds the payload, calls Session 14's API client, and atomically (one `$transaction`) writes the `NerisSubmission` row, transitions `Incident.reviewStatus` via a guarded `updateMany` (optimistic-locking, same pattern as every other transition in this file), and writes a `ReviewEvent` when there's a real actor. It never throws — every failure mode (payload-build failure, missing credentials, non-201 response, thrown network/auth error) is caught internally and recorded as a normal `ERROR` outcome, consistent with `notify.ts`'s "a side effect must never make the calling action's promise reject" principle, except here the "side effect" *is* the actual status transition the plan asks for, so it converts failures into a real, correctly-recorded state rather than swallowing them silently.
- **The optimistic-locking guard uses the incident's own current `reviewStatus` as both the `updateMany` `where` condition and the `ReviewEvent.fromStatus`, not a hardcoded `'APPROVED'`.** This is what lets one function correctly serve both `APPROVAL_AUTO`/`SCHEDULED_SWEEP` (starting from `APPROVED`) and `MANUAL_RESEND` (starting from `ERROR`) without a trigger-specific branch — confirmed by a dedicated test (`'uses ERROR as the fromStatus when resending a previously-failed incident'`).
- **A real, deliberate, disclosed gap: `ReviewEvent` is not written for `SCHEDULED_SWEEP`.** `ReviewEvent.actorId` is a required (non-nullable) FK to `User` — there is no "system" actor concept anywhere in this schema, and this session's own scope doesn't include a schema change to add one. A cron-triggered retry has no human to attribute the transition to, so `recordSubmission` only writes a `ReviewEvent` when `actorId` is non-null (true for `APPROVAL_AUTO`, since the approving user IS the actor of the same logical action, and for `MANUAL_RESEND`, since a real Chief/Admin clicked the button) — for `SCHEDULED_SWEEP`, the `NerisSubmission` row itself (`trigger`/`createdAt`/`succeeded`) is the audit record instead. `CONTEXT.md`'s Workflow section is updated to describe this exception explicitly rather than leaving its "every status transition" claim now-slightly-wrong.
- **A real, pre-existing test broke as a direct, correct consequence of this session's change — found and fixed, not left red.** `test/db/review-queue.db.test.ts`'s solo-department test called the real `approveIncident` against a real Postgres department with no NERIS credentials configured, and asserted the incident ended up `APPROVED`. It now correctly ends up `ERROR` (the department has no `nerisFdId`/credentials, so `attemptNerisSubmission`'s "credentials not configured" branch fires) — this is Session 15 doing exactly what it was supposed to, not a bug. Updated the test's assertions to match the new, correct behavior (checks `approvedById` still gets set, the event chain now includes a third `APPROVED->ERROR` entry, and a `NerisSubmission` row exists) rather than declaring the old, now-obsolete assertion the source of truth. Same shape as Session 1/2's dispatch-fixture staleness findings — grep found only this one file affected (the E2E suite never drives an incident through Approve today, so nothing else needed touching).
- **Scheduled sweep is genuinely new infrastructure, exactly as flagged as a possibility in this session's own instructions** — no `app/api/*` route, no `vercel.json`, existed before this session. `app/api/neris/sweep/route.ts` is a plain `GET` Route Handler, gated on `Authorization: Bearer $CRON_SECRET` (a new env var); `vercel.json` schedules it nightly (`0 6 * * *`) via Vercel Cron, the natural fit given this app's existing Vercel hosting. **Vercel's documented behavior — that it automatically sends `Authorization: Bearer $CRON_SECRET` on cron-triggered requests once that env var is set on the project — is unverified against a real Vercel deployment in this session** (no way to trigger a real Vercel Cron invocation from this sandbox); the route's own auth check is straightforward and independently correct regardless (rejects anything without a matching bearer token), so the only real unknown is whether Vercel's side of the contract matches the documented behavior this route relies on.
