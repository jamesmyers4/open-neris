# TEST-PLAN-CONTEXT-HISTORY.md

Full revision log for TEST-PLAN-CONTEXT.md, split out once the inline log
got long enough that reading it top-to-bottom stopped being necessary to
use the tool - same progressive-disclosure principle the doc already
applies elsewhere (references/ files loaded on demand rather than held in
one file). The main doc keeps a short "recent changes" summary and a
pointer here; this file is the full archival detail, read only when
someone actually wants the history.

- **v0.7 (this revision).** Run against `open-neris-app` — the user's own actively-developed project, not a disposable fork of a published spec, and the first target with real, non-published business logic (a department review workflow with no NERIS-defined counterpart) sitting alongside a genuinely external spec (NERIS field semantics) for other parts of the same app. Planning and all six implementation phases happened in prior sessions; this revision comes from a follow-up session that (a) audited the DB-reachability wording added in v0.6 against a direct question — would a `test-plan` run have proposed DB-direct tests from the document alone, without the dev also saying so out loud — and (b) turned `TEST-PLAN.md`'s "Deferred / flagged" backlog into a second wave of numbered phases. On (a): the audit's conclusion is yes, on balance — the Scan step already instructed identifying reachable layers and defaulting to direct coverage where the DB is reachable, and the Interview unconditionally asks for temp-DB strategy whenever a real DB is in the stack — but the instruction lived as a sub-clause inside a paragraph rather than as a first-class taxonomy line or a tightened interview trigger, which is thin enough to not fully trust across a stack this project hasn't tried yet. Tightened both: added an explicit "DB-direct / schema-constraint tests" taxonomy line, and changed the Temp/test DB strategy interview question's trigger from "a real DB is in the stack" to "a real DB is in the stack and was identified as directly reachable in the Scan step" — wiring the two steps together explicitly instead of leaving the connection implicit. On (b): reframed `TEST-PLAN.md`'s lifecycle — it is not reliably a write-once, delete-when-phases-complete document; a deferred or gate-blocked item becoming actionable later reactivates it into a new numbered phase block in the _same_ file rather than spinning up a parallel doc, and this is now stated explicitly rather than left to guesswork the first time it happened. Named this reactivation as a mode of `test-plan` itself — re-verify whatever gating condition originally blocked the item, skip the Scan/Sweep steps for items already inventoried, and continue phase numbering — rather than proposing it as a separate skill; the judgment involved (three-tier discipline, sequencing) is the same job, just applied to a known subset instead of a fresh full sweep. Also introduced "blocked phase" as a plan primitive distinct from "sequenced-later phase": a blocked phase names an exact, re-checkable external condition (a specific section of a specific doc, a feature's existence) rather than a vague "once things stabilize," and can't be pulled forward by any sequencing-philosophy reasoning the way a merely-later bootstrap-mode phase can. Drafted `TEST-MAINTAIN-CONTEXT.md` v0.1 — pure design, no validation runs, grounded in this project's own `TESTING.md`/`TEST-PLAN.md` artifacts rather than invented from scratch. Finally, revisited the standing "guardrail never fires" open question with a rival hypothesis this run surfaces but can't confirm: this target's real ambiguities (whether `module-relevance.ts`'s baseline module set matched NERIS's own CSVs; whether a counter-bucketing quirk was intentional) were resolved live during the _planning_ interview, before implementation ever started, not mid-implementation — raising the possibility that a guardrail never firing during `test-implement` might mean planning is front-loading ambiguity resolution correctly, independent of whether the target has a published spec, rather than meaning the guardrail's trigger conditions themselves are miscalibrated. Not confirmable from this run alone since decisions were made in a prior session this one didn't have transcript access to — logged as a rival explanation to weigh in the next run, not a resolution.
- **v0.6.** Added an explicit position: this tool's job is a strong initial layer of coverage, not 100% in one pass — that's unrealistic regardless of how many phases a plan has, and the doc previously implied completeness as the goal without saying so. Coverage is expected to keep growing across future sessions, real-world bug reports, and periodic re-runs; `test-maintain`'s eventual role likely needs to include treating a reported bug as a trigger to add a regression test, not just as something to fix. Added explicit UI/API/DB layer-reachability assessment to the scan step — not every layer is always directly testable (access limits, or by design), and where a layer _is_ reachable (most often the DB), it should get direct coverage rather than being tested only incidentally through the API layer above it. Added a bounded self-review pass (up to 2-3 iterations) as an explicit closing step for `test-implement` — reviewing the suite's own output for redundancy, consistency, and gaps within already-covered areas before handoff, distinct from adding more phases. Also named, explicitly, a real gap this revision does not resolve: everything validated so far assumes an existing codebase to scan, whether thin or mature. A greenfield target with a schema but no built application has no clean mapping onto bootstrap sequencing as currently defined — that's a different problem (tests as spec, driving what gets built, closer to literal TDD) and deserves real design before this process gets pointed at one, not a forced fit. See Open questions. Reframed the guardrail question rather than just logging a third non-firing. Likely structural reason: every implementation run so far (django, rails) has been against a RealWorld/Conduit implementation — a crisp, externally-published spec, which makes every finding a "does this match documented behavior, yes or no" question. That's never actually ambiguous once confirmed, only unplanned. Real ambiguity needs either genuine business logic with no external spec to check against, or real external stakes (payments, email, third-party APIs) where mock-vs-real is a judgment call rather than a lookup — both were criteria proposed early in this project and set aside in favor of verifiable, controlled-comparison targets. Noted explicitly as a candidate-selection blind spot, not a flaw in the runs themselves. Separately, added a second, independent trigger alongside the ambiguity-based guardrail: severity-triggered prominent flagging, regardless of whether the disposition was clear — the Rails run's best instinct (surfacing its most severe finding loudly in chat despite not stopping) wasn't something the doc asked for, and should be.
- **v0.4.** Split the Runtime Viability Check's single "record the ceiling" instruction into two real findings from the Rails run: the _verification environment_ can decay independently of the app's own dependencies (EOL base images, dead package mirrors — distinct from, and compounding on top of, the app's pinned-dependency ceiling), and a floating Docker tag isn't a stable reference over time, so the resolved patch version and check date now have to be recorded, not just the minor line. Added an explicit scope boundary for planning-time runtime verification (confirm specific already-surfaced findings cheaply; no open-ended exploration — that's `test-implement`'s job). Generalized the security-relevant infer-but-confirm carve-out to any characterized-as-current-behavior finding under autonomous commit mode — this was already happening in practice on the Django run (its own bug-characterization convention never actually had a security qualifier), so this catches the doc up rather than changing behavior. Added a reproduced-vs-inferred-only confidence label to infer-but-confirm findings. Clarified that "E2E happy path" gets reinterpreted (request-spec-level journeys) rather than marked N/A for UI-less backends — N/A is reserved for categories with no possible referent at all. Clarified sequencing order and coverage depth are independent axes; layer order isn't a priority ranking.
- **v0.3.** `test-implement` is no longer unvalidated — six phases executed, 135 tests landed, phase-sizing floor held under "let the plan decide," and two entirely new bugs surfaced during implementation that planning never predicted (the value case for actually executing a plan, not just writing one). Corrected the v0.2 claim that CONTEXT.md grows "the same way TESTING.md already does" — it doesn't: CONTEXT.md's growth is gated on hitting a new fact about the app specifically, arrives in bursts rather than steadily, and can require rewriting an earlier entry, not just appending to it, unlike TESTING.md's purely additive checklist. Tightened the coverage sweep to require cross-referencing an actual route list for API/E2E layers, after a real endpoint went untested for four phases under feature-block-level description alone. Added a rule that CI configuration must reuse whatever runtime the Runtime Viability Check already verified rather than reimplementing its own setup — confirmed necessary, not theoretical, after a CI job that used `actions/setup-python` instead of the verified Docker container failed once GitHub's runner image stopped shipping that Python version. The stop-and-ask guardrail remains the one substantial thing this run didn't validate — six phases and five in-flight corrections, and it never fired once — now the explicit target for the next run rather than a byproduct to hope for.
- **v0.2.** Incorporated findings from the `django-realworld-example-app` run: added "not applicable" as a third resolution path for always-ask questions with no live referent (distinct from "the repo already answered this"); added a conditional Runtime Viability Check pre-step for repos that don't already run; reframed the authorization/boundary-testing taxonomy entry to explain _why_ it gets sequenced early, not just that it's commonly skipped; required recommended defaults to be presented as pre-selectable options in the interview, not free text; clarified that CONTEXT.md is created (even as a minimal stub) during the planning session itself when none exists, and is expected to grow during implementation the same way TESTING.md already does. Also added a phase-sizing floor note (single-sitting sizing remains the default even under "let the plan decide") and a rule for security-relevant infer-but-confirm items, both from reviewing the plan itself rather than the run's self-reported feedback.
