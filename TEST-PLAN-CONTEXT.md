## What this is

A Claude Skills plugin that assesses a codebase (existing or greenfield) and produces a governing test automation plan — the process and judgment calls a QA lead makes doing a test-automation intake, encoded as something repeatable rather than one-off consulting. The deliverable of a planning run is a document Claude Code can execute against in phased, committable sessions, plus a living doc that stays current as implementation proceeds. **The goal of any single run is a strong initial layer of coverage — the obvious cases and a good share of the non-obvious ones across every reachable layer — not 100%.** Full coverage in one pass isn't realistic at any reasonable phase count, and treating it as the bar would be its own kind of dishonesty about what got tested. Coverage is expected to grow over time: repeat sessions, `test-maintain` picking up conventions on later work, and — importantly — real-world bugs and customer reports functioning as a legitimate trigger to add a regression test, not just to patch the code and move on. QA is an ongoing practice, not a one-time deliverable; this tool is meant to establish that practice cheaply, not to front-load its entire lifetime of coverage in a single session.

## What this isn't

Not another "write me a test" generator. Several of those already exist — Playwright spec generators, Jest-to-Vitest migration skills, framework-specific test writers. This project sits a layer above that: it decides _what_ needs coverage, _in what order_, _with which tools_, and _under what constraints the dev actually has_ — the judgment work, not the typing work.

## Vocabulary

- **Planning session** — the pass where `test-plan` scans the repo, resolves the three-tier discipline, interviews the dev on what can't be inferred, and writes TEST-PLAN.md.
- **Implementation session** — a `test-implement` run that reads TEST-PLAN.md, executes the next open phase, and updates TESTING.md. Validated on `django-realworld-example-app`: six phases, one commit each, no stops. See Dogfeeding plan below.
- **Three-tier discipline** — the rule set governing what gets inferred silently, confirmed with the dev, or must be asked outright.
- **Runtime viability check** — a conditional pre-step: confirming the app can actually run at all (and on what runtime version) before anything else proceeds. Only fires when the app doesn't already run; most real repos skip it entirely.
- **Golden master** — a checked-in snapshot of current, pre-existing, deterministic behavior used as a baseline when there's no spec to test against. Scoped narrowly to deterministic behavior — see the taxonomy entry below for how it relates to non-deterministic AI output.
- **Coverage sweep** — the completeness pass across the full taxonomy, done _before_ any sequencing decision.
- **TEST-PLAN.md** — the planning session's output. Phases, decisions, interview answers, sequencing. Written once, revised occasionally, not continuously updated. **Not reliably a delete-when-done document** — an item deferred or blocked in the original pass can be reactivated later into a new numbered phase block in the same file once its gating condition changes, rather than starting a parallel doc. See "Resuming deferred or blocked work" under `test-plan` below.
- **Blocked phase** — a plan primitive distinct from a merely-later, sequenced phase. Names an exact, re-checkable external condition (a specific section of a specific doc, a feature's existence) that has to change before the phase can start at all. Unlike ordering within bootstrap or gap-closure sequencing, no amount of sequencing-philosophy reasoning can pull a blocked phase forward — only the named condition resolving can.
- **TESTING.md** — the living doc. Created and updated during implementation sessions: current coverage state, how to run the suite, conventions, open findings.

## Architecture — the skills

### `test-plan` (user-invoked)

Does the scan, the coverage sweep, the three-tier resolution, the interview, and the sequencing pass. Writes TEST-PLAN.md. **Creates a CONTEXT.md — even a minimal stub, if the repo has none — during the planning session itself, not deferred to implementation.** It grows during implementation, but not the way TESTING.md does — TESTING.md is a purely additive checklist, while CONTEXT.md's growth is gated specifically on hitting a new fact about the _app_ (not the process), arrives in bursts tied to whichever phase happens to exercise the relevant code path rather than steadily, and can require rewriting an earlier entry rather than just appending to it — a status-code note discovered narrow in one phase turned out to need broadening once a later phase tested a wider case. Both docs stay current; they don't stay current the same way. Touches an existing CLAUDE.md or CONTEXT.md only with explicit confirmation. Internally organized around domain-specific reference files (see Stack reference matrix) rather than one skill per domain — the domains aren't independent, a DB choice affects both API test-data strategy and E2E seeding, and a single pass reasoning across all of it avoids stitching together disconnected assessments afterward.

**Resuming deferred or blocked work (a mode of `test-plan`, not a separate skill).** First real instance on `open-neris-app`: a follow-up session turned the original plan's "Deferred / flagged" backlog into a second wave of numbered phases continuing from the last completed one. The judgment involved is the same as a fresh planning pass — three-tier resolution, sequencing — just applied to an already-inventoried subset instead of a full sweep, which is why this doesn't warrant its own skill. What actually differs from a fresh pass: (1) re-verify whatever gating condition originally blocked each item — don't assume it's still true just because the plan said so weeks or months earlier; (2) skip Scan/Sweep for items the original pass already inventoried, unless the repo has changed enough that the inventory itself is suspect; (3) continue phase numbering in the same file rather than starting a parallel doc; (4) any bug that was characterized-not-fixed in an earlier phase gets its fix-vs-continue-defer disposition asked as a live, explicit decision at resume time — it doesn't get silently pre-resolved by whoever writes the resumed phase list, and it doesn't get silently bundled into unrelated phase work either.

### `test-implement` (user-invoked, thin)

Opens TEST-PLAN.md, finds the next unchecked phase, executes it under whatever commit-mode was recorded during planning, updates TESTING.md and CONTEXT.md as it goes. Most of its value is discoverability plus **two independent triggers for interrupting an otherwise-autonomous run**: stop and ask when the _right action_ is genuinely unclear (the original guardrail), and separately, flag prominently — in chat, not just in the observations log — when a finding is _severe_, regardless of whether its disposition was clear. These are different reasons to interrupt; a bug can be unambiguously "characterize, don't fix" and still be important enough that burying it in a markdown file isn't enough. **Once every phase is complete, a bounded self-review pass (up to 2-3 iterations) closes out the run** — reviewing the suite's own output for redundancy, naming consistency, and gaps within areas already marked covered, before handing off. This is quality review of what was written, distinct from adding new phases or new coverage — a second look at the same ground, not more ground. Validated on `django-realworld-example-app` and `rails-realworld-example-app` — thirteen phases combined, 250 tests, no ambiguity-triggered stop across either run despite the second run's kickoff prompt deliberately engineering a live decision and surfacing this project's most severe finding to date (a Devise session cookie silently overriding a different user's JWT after signup). See Dogfeeding plan and Open questions for what that pattern actually seems to mean.

### `test-maintain` (model-invoked, tiny)

"If this repo has a TESTING.md, read it before touching test code." No dedicated command. Per skill-creator guidance, model-invoked skills tend to undertrigger — this one will need real trigger evals once it exists, not just a plausible-sounding description.

## Process — `test-plan`

0. **Runtime viability check (conditional).** Only fires if the app doesn't already run. Attempt the app's existing build/run commands; if they fail, diagnose why (missing dependency, incompatible language-runtime version against a pinned framework version, etc.) and record the finding. **Two distinct sources of "won't run" to check for, not one:** the app's own dependency ceiling (a pinned framework capping the usable interpreter version), and the _verification environment's_ own decay — an EOL base image, dead package mirrors, expired signing keys — which is independent of the app's code and compounds over time regardless of it. Record whichever is actually blocking, not just the first one found. **Record the exact resolved version and the date checked, not just the minor line** — a floating Docker tag (`ruby:2.3`) can resolve to a different, possibly-broken patch a year from now even though the app hasn't changed; "confirmed against `ruby:2.3`, which resolved to `2.3.8` on 2026-08-15" is the actual finding, "confirmed against 2.3" isn't specific enough to be reproducible later. **Scope boundary:** runtime verification at planning time is for establishing the ceiling and cheaply confirming specific findings the coverage sweep already surfaced (a suspected bug worth one quick reproduction, say) — not open-ended exploration or writing throwaway test code, which is `test-implement`'s job. **Whatever runtime this step verifies (a container, a pinned interpreter version, whatever) is the runtime CI must actually use.** Confirmed the hard way: a CI job that reimplements its own environment setup instead of reusing the verified one is a real, recurring failure mode for pinned-legacy-runtime repos, since hosted-runner base images move forward over time and can drop support for versions that worked fine at verification time. If CI can't run the app's own build/test entrypoint (a Makefile target, a script) inside the same environment this step verified, that's a gap in the plan, not an acceptable shortcut. Most real repos skip this whole step entirely, since having a running app is usually a precondition for someone caring about adding tests in the first place.
1. **Scan.** Read the repo before asking anything. Languages, frameworks, existing test config, CI config, folder conventions. **Identify which architectural layers are actually directly reachable for testing — UI, API, and DB are the three that matter most.** Not every layer is always testable directly: sometimes DB access is genuinely unavailable (a managed database with no direct connection, credentials the test environment doesn't have), sometimes it's unreachable by design. Where a layer _is_ reachable — most often the DB — plan direct coverage against it rather than defaulting to API/E2E tests as the only lens and treating DB behavior as merely implied by whatever passes through the API above it. A migration bug or a constraint violation can be invisible to an API-level test that happens to route around it. **This finding must survive into the Coverage sweep as its own taxonomy line (see below), not just live as a fact noted during the Scan** — a reachability finding that only exists as a sentence in step 1 is one rewrite away from being lost by the time sequencing happens in step 5.
2. **Coverage sweep.** Walk the full taxonomy and inventory what needs coverage and what already has it. This step is about completeness, not order. For E2E and BDD layers specifically, verifying coverage means reading test titles and selector/page-object usage inside the files, not diffing directory listings against the taxonomy. Any claim in the repo's own docs about cross-suite correspondence is a hypothesis to verify, not a fact to inherit. **For API/E2E layers, describe coverage against an actual enumerated route list (the router/urls file, not a feature-block summary)** — `django-realworld-example-app`'s Phase 2 was scoped as "articles integration tests" and never named `/api/articles/feed` as a specific route to hit, and it went completely untested for four phases until an unrelated E2E flow stumbled onto it. Feature-block-level description is coarse enough to hide an entire endpoint; a route list isn't.
3. **Three-tier resolution.** For everything found in step 2, resolve it via the discipline below.
4. **Interview.** Ask whatever step 3 flagged as always-ask. Recommended defaults are presented as pre-selectable options, not open-ended free text — this is a requirement for how the interview is presented, not just a nice-to-have; it's what keeps a several-question interview down to a handful of quick selections instead of essay answers.
5. **Sequencing pass.** Decide phase order using the sweep and interview answers — see the two named modes below.
6. **Write TEST-PLAN.md.** Phases, decisions, interview answers (including anything requiring manual external setup, flagged clearly), sequencing.
7. **Touch adjacent docs per the collision policy** — extend CLAUDE.md and an existing CONTEXT.md only with explicit confirmation; create a minimal CONTEXT.md stub if none exists at all (not gated behind confirmation, since there's nothing to overwrite); handle any existing TESTING.md-equivalent per its own policy below.

## Three-tier inference discipline

- **Always infer, never ask** — languages and frameworks in use, existing test runner config, CI config, folder conventions. Reading `package.json` / `.csproj` / CI YAML, not judgment.
- **Infer, but confirm** — anything that looks unintentional, half-finished, or buggy. Flag it ("found X — intentional, or a known issue?") rather than testing the bug as if it were spec, or silently guessing which one it is. **Label each flagged finding by how it was established** — reproduced directly (ran it, watched it fail) versus inferred from reading the code alone — since these carry real, different confidence and a plan shouldn't present a strong guess with the same certainty as a confirmed fact. **Any finding characterized as current-possibly-wrong behavior gets a treatment that can't be mistaken for a clean pass** — an `xfail` with a reason, or a test explicitly named to flag the known issue (`test_KNOWN_BUG_no_ownership_check`, for example) — rather than a plain green assertion. Not limited to security-relevant findings: a plain crash bug hidden behind a passing test is just as misleading as an authorization gap, and this is already how the tool behaves in practice, not just a stated rule. This matters most precisely when commit mode is autonomous and nothing is necessarily reviewed before landing.
- **Never infer, always ask** — team size, risk tolerance, budget for paid tooling, timeline, whether the codebase is pre-launch or production-critical, and the interview question set below. Two carve-outs:
  - **Already documented.** If the repo has already unambiguously documented an answer to a specific always-ask question in its own docs, don't pose it as a blank open question — treat it like infer-but-confirm instead: state the inferred answer, cite the source, and ask only for correction.
  - **Not applicable.** Some of these questions assume a live team and product roadmap behind the repo at all — team size, budget, timeline, pre-launch-vs-production. For a fixed archival, teaching, or QA-target repo, there may be no team to ask and no launch to plan around. In that case the answer isn't inferred _or_ asked — it's marked not applicable, with one line of stated reasoning, rather than silently dropped or asked as if a real answer were expected.

## Coverage taxonomy

- Unit tests
- Integration / API contract tests
- **DB-direct / schema-constraint tests** — for any layer the Scan step identified as directly reachable (most often the DB): constraints, cascades, migrations, and any raw-SQL or non-ORM logic, tested against a real (ephemeral) instance rather than only inferred through whatever an API/service layer happens to pass through it on the way past. A first-class taxonomy line specifically so a Scan-step reachability finding can't quietly fail to make it into the Coverage sweep or the sequencing pass.
- E2E happy path — **for a UI-less backend, this category gets reinterpreted, not marked N/A**: a full multi-request journey at the request-spec/API-client level, rather than browser-driven. N/A is reserved for categories with no possible referent at all once there's no UI (Accessibility, Cross-browser, Visual regression below) — those are a genuinely different situation from "has no UI to drive, but the underlying user journey still needs exercising."
- Edge, negative, and boundary cases
- Accessibility (WCAG / Section 508)
- **Golden master / characterization** — for pre-existing, _deterministic_ behavior with no real spec to test against. Narrowly scoped: pinning exact output as correct-by-definition. Related to, but distinct from, AI/LLM output testing below — same underlying motivation, different technique, because the failure mode flips when output is expected to legitimately vary between runs.
- **Authorization / boundary testing** — can role or tenant A see or act on role or tenant B's data. Disproportionately likely to contain a real, currently-shipping bug when it hasn't been tested — not merely a commonly-skipped category, but one where the absence of coverage and the presence of an actual defect tend to go together. Sequence it earlier than typical edge-case work in a bootstrap run for that reason, not only because it's often missed.
- Cross-browser / responsive
- **AI/LLM pipeline output testing** — for pipelines with non-deterministic output. Reusable pattern (generalized from Drover's Grader subsystem): treat this as grading pre-supplied `{input, output, rubric}` triples via LLM-as-judge — the test doesn't generate the output itself, an adapter or fixture supplies input/output pairs, and grading is a pure function over them. Use more than one judge model or model-family per check rather than a single judge, to guard against single-model bias. Keep hosted-API-cost grading opt-in or scheduled, not blocking on every push, and gate escalation to a hosted judge behind an explicit data-sensitivity flag if the content being graded could be sensitive. A "skipped" outcome is a legitimate first-class result for a check, not a failure.
- Visual regression — optional, flagged rather than default-on (tooling/cost overhead)
- Performance / load — optional, flagged rather than default-on, same reasoning

## Sequencing philosophy

Decided last, after the coverage sweep — not first. Two named modes, both now validated against a real run:

- **Bootstrap sequencing** — for repos where the sweep comes back mostly Gap. Fast, isolated, deterministic layers first (unit, API/integration), since they usually become fixtures the E2E layer reuses. Then integration, then E2E happy path, then edge cases and grey-area coverage, then optional layers last. Validated on `django-realworld-example-app`. **This ordering is about fixture dependency, not priority** — coming last doesn't mean optional or skippable. A "thorough everywhere" depth answer (see interview) doesn't change this order, it changes how much scrutiny each stage gets once reached; the two are independent axes, confirmed on `rails-realworld-example-app` where "thorough everywhere" turned the edge-case phase into a fully-scoped, must-complete phase rather than a time-permitting tail.
- **Gap-closure sequencing** — for repos where the sweep comes back mostly Covered. Order by: fix any stale baseline first, then novel/high-value gaps per the risk-tolerance answer, then CI-signal-timing gaps, then lower-stakes/smoke-tier items last. Validated on Shenny.

**Phase-sizing floor.** "No strong preference — let the plan decide" resolves _what_ defines a phase boundary (natural coverage boundaries versus a stated time-box) — it is not license for a phase to grow unbounded. Single-sitting-sized phases remain the implicit default even under this option; only the explicit "long sessions" answer licenses multi-phase-per-sitting sizing. Whether this is actually being respected in practice, or whether "let the plan decide" quietly produces an oversized first phase by default, is open — `django-realworld-example-app`'s Phase 0 (test-framework scaffolding, fixtures, a Docker test-runner target, and a full CI workflow all in one phase) is a plausible instance of the latter, but this can only really be confirmed once a phase is actually executed by `test-implement` rather than just planned.

**Resolved:** the exact bootstrap/gap-closure threshold remains open, but both modes are now real, validated outcomes rather than a theoretical split — one data point each, in opposite directions.

## Pre-existing doc handling

- **Existing TESTING.md-equivalent** — default is to suggest a rename for portability. If the dev wants to keep their own name, record the actual filename as a pointer instead of forcing it. If none exists, it's created during implementation, not planning.
- **Existing CLAUDE.md or CONTEXT.md** — per-file, explicit confirm: append a testing-vocabulary section, write a separate doc, or skip. Never silently overwrite a doc the dev already owns. **If no CONTEXT.md exists at all, create a minimal stub during the planning session** (not gated behind confirmation, since nothing is being overwritten) and expect it to grow during implementation as discoveries happen — see Architecture above.

## Stack reference matrix (seed)

Strategic shape comes first; this exists so it has somewhere to grow, not as an exhaustive catalog. Once `test-plan` is actually built, each row family becomes its own file under `references/`, loaded only when the scan finds a match.

**Lookup is tiered, not either/or.** Check this matrix first — fast, no network dependency, no risk of stale or hallucinated tooling advice, and it carries real hard-won lessons (framework-level gotchas like DRF's 403-vs-401 coercion or Django's `__classcell__` ceiling) that no web search would surface, since those only exist because something actually ran the code and hit them. If the detected stack isn't in the matrix, fall back to a live search for current tooling conventions — but treat whatever comes back as a hypothesis to verify against the actual scan, the same epistemic posture the doc already takes toward a repo's own self-claims, not as settled fact because it came from the internet. Either way, the Scan step's own investigation of _this specific app_ is never replaced by either the matrix or a search — both only seed tooling choices and known framework-level behavior, not app-specific findings. Close the loop: a run against a genuinely new stack should propose its generalizable findings as a new matrix entry when it's done, not leave that to happen by hand.

### Common full-stack combinations (recognize-by-name)

Useful for the scan step to recognize an entire stack at once — a repo's `package.json`/lockfile/build-file combination usually maps directly onto one of these:

- **LAMP/LEMP** (Linux + Apache/Nginx + MySQL/MariaDB + PHP) — still the largest single population of live websites; low cost, huge legacy footprint, includes classic WordPress/Drupal-style CMS stacks.
- **Next.js + PostgreSQL** (+ Vercel, Prisma/Drizzle, Tailwind) — de facto modern default for new SaaS/web apps. Shenny's own family.
- **T3** (Next.js + TypeScript + tRPC + Prisma/Drizzle + Auth.js) — end-to-end-typed variant of the above, common among TS-first indie/startup teams.
- **JAMstack** (Next.js/Astro/SvelteKit + headless CMS + edge/CDN) — static-first, content/marketing-heavy sites.
- **MERN / MEAN / MEVN / PERN** — Node + Express + {React/Angular/Vue} + {MongoDB/Postgres}. PERN swaps Mongo for Postgres and leans more relational/enterprise than the others.
- **Python (FastAPI or Django) + Postgres** (+ React/Next.js frontend) — FastAPI leans async/model-serving/AI-adjacent backends; Django leans CRUD/admin-heavy apps. `django-realworld-example-app` is a real (if dated — Django 1.10) example of this family, API-only.
- **Laravel (PHP) + MySQL/Postgres** — modern PHP, frequently deployed on LAMP/LEMP infra underneath.
- **Ruby on Rails + Postgres** — convention-over-configuration, strong for MVP/full-featured SaaS.
- **.NET (ASP.NET Core + C#) + SQL Server/Postgres**, often paired with Angular, React, or Blazor — enterprise/government-heavy.
- **Java + Spring Boot + Postgres/Oracle**, paired with React/Angular — the enterprise/regulated-industry workhorse.
- **Nuxt (Vue) or SvelteKit** — full-stack meta-framework counterparts to Next.js.
- **Go + Postgres**, often behind a separate frontend — high-performance microservices/APIs/CLIs.
- **Phoenix (Elixir) + Postgres** (+ LiveView) — highly concurrent, minimal-JS real-time UIs.
- **Serverless/edge** (Cloudflare Workers, Vercel Edge, AWS Lambda + D1/Postgres/KV) — latency-sensitive, globally distributed.
- **AI-native/hybrid** (Python/FastAPI or Node orchestration + vector DB + LLM SDKs + React/Next.js frontend) — Shenny is a real example of this layered on top of Next.js.
- **Mobile** — React Native + Expo, Flutter, or native (Swift/SwiftUI, Kotlin/Jetpack Compose) for performance-critical or hardware-heavy apps.

Useful priors regardless of which combination a repo turns out to be: TypeScript has functionally superseded plain JS for serious new work, PostgreSQL is the leading relational choice among professional teams even where a stack's "classic" name says MySQL or Mongo, and Docker is close to universal. **For older or archived stacks specifically, the pinned framework version may cap the newest usable language-runtime version** — `django-realworld-example-app`'s pinned Django 1.10 tops out at Python 3.7 (3.8+ breaks on a `__classcell__`/metaclass change Django's Python-2/3 compat layer at that version doesn't survive) — which is exactly what the Runtime viability check step exists to catch and record.

### By domain (component-level detail once a combination is recognized)

**Frontend:** React (CRA/Vite), Next.js, Angular, Vue/Nuxt, Svelte/SvelteKit, static/vanilla, legacy jQuery
**Backend:** Node (Express/Fastify), .NET (ASP.NET Core), Python (Django/Flask/FastAPI), Java (Spring), Ruby on Rails, PHP (Laravel/legacy)
**Database:** PostgreSQL, SQL Server, MySQL, SQLite, MongoDB
**E2E:** Playwright (recommended default for anything modern); Selenium (legacy — migrate-in-place for new specs, don't rip out a working suite); Cypress (alternative, flag ecosystem overlap with Playwright)
**Unit/integration:** Vitest (recommended default, current JS/TS); Jest (legacy JS/TS, document a migration path); xUnit/NUnit/MSTest (.NET); pytest (Python — used for `django-realworld-example-app`'s Phase 0/1, alongside `pytest-django`); JUnit (Java); RSpec (Ruby)
**BDD/Cucumber-family:** Cucumber.js (JS/TS), Reqnroll/SpecFlow (.NET), behave (Python), Cucumber-JVM (Java) — gated behind the interview question, not default-on
**CI/CD:** GitHub Actions (default absent a strong reason otherwise), GitLab CI, Azure DevOps, CircleCI, Jenkins (legacy/on-prem)
**Environment/infra:** Docker Compose (default recommendation for ephemeral test environments, not a mandate — defer to a repo's own already-established devcontainer, Nix, or venv/nvm-style setup rather than overriding it), Kubernetes (namespace-based test environments for larger orgs), serverless/edge deploy targets (needs a preview-environment-based approach, not local container spin-up), Testcontainers (recommended default wherever a real DB needs to sit inside a test run)

## Open questions / ADR candidates

- Whether `test-plan` / `test-implement` should ship as two skills or collapse into one — current lean is two, thin.
- Project name and whether the skills get a shared namespace prefix once it's chosen.
- `test-maintain`'s trigger reliability — still unvalidated, needs real trigger evals once it exists.
- **The stop-and-ask guardrail has never fired, across three runs, and the reason now looks structural rather than a matter of not having tried hard enough.** Django: six phases, five in-flight corrections, none ambiguous. Rails: seven phases, six bugs including this project's most severe finding, plus a kickoff prompt specifically engineered to force a live decision on a known bug — still zero stops, and the implementer's own stated reasoning was that "unanticipated" and "ambiguous what to do about it" turned out to be different properties in both runs. Likely cause: both implementation runs are against the RealWorld/Conduit spec, which is crisp and externally published — every finding so far has been "does this match documented behavior," which is never actually ambiguous once confirmed. Two candidate criteria for a target that could actually produce real ambiguity, both proposed early in this project and set aside for good reasons (verifiability, controlled cross-stack comparison) that no longer clearly outweigh three runs of the same null result: **genuine business logic with no external spec to check against** (what "correct" means has to come from domain judgment, not a published contract), or **real external side effects with real stakes** (payments, email, third-party APIs — mock-vs-real is a judgment call, not a fact to look up). Worth treating as the primary selection criterion for the next target, not a secondary one.
- **Severity-triggered flagging, distinct from the ambiguity guardrail — new in v0.5.** The Rails run's best instinct (surfacing its most severe finding prominently in chat despite the disposition being clear) wasn't something the doc asked for. Now a named second trigger in the architecture section. Unvalidated by design — needs a future run to actually confirm it fires when it should, the same way the original guardrail needed real runs to validate.
- The bootstrap/gap-closure sequencing threshold — two validated data points, exact boundary still unknown.
- Phase-sizing floor under "let the plan decide" — **resolved, one data point.** Held for all six phases on `django-realworld-example-app`, including the phase flagged beforehand as a plausible oversized-first-phase risk. Not proof it always holds, but the specific concern raised in v0.2 didn't materialize.
- **No shape yet for a greenfield, spec-only target — deliberately deferred, not designed under time pressure.** Everything validated so far (Shenny, django, rails) assumes an existing codebase to scan, thin or mature. A repo with a real schema and validation layer but no built application yet doesn't cleanly map onto bootstrap sequencing — there's no application behavior to sweep, characterize, or sequence against. The actual problem in that situation is closer to literal TDD: tests as the spec that drives what gets built, not tests as verification of what already exists. Motivating case: `open-neris`, a real project in active early development (schema and validation done, app not built). Worth designing this as its own mode deliberately — what the schema/validation layer stands in for as "the spec" in place of a published API contract, what "coverage sweep" even means with nothing to sweep, and how commit-mode/autonomy defaults should differ against a live, actively-developed project instead of a disposable fork of someone else's abandoned repo — rather than forcing the existing 7-step flow onto a target it wasn't built for.
- Distribution — Matt Pocock's `mattpocock/skills` ships via `npx skills add` plus the official `claude.com/plugins` marketplace. Precedent worth using later; not a v0 concern.
- **`TEST-MAINTAIN-CONTEXT.md` exists now as a v0.2 draft but is pure design — zero validation runs.** Its central open question is the same trigger-reliability problem `test-maintain` itself already carried in this doc, now with a first, untested set of candidate trigger conditions. Needs a real run before any of those candidates can be trusted. **Resolved as of v0.8**, though: gate-flip detection belongs in `test-maintain` (mechanically checkable, same shape as its other triggers) but execution doesn't — a detected gate flip surfaces a nudge to run `test-plan`'s resume mode, it doesn't trigger the resume itself. Keeps the advisory/non-blocking character intact rather than quietly turning `test-maintain` into `test-implement` running unattended.
- **Front-loaded ambiguity resolution as a rival explanation for the guardrail never firing** — new in v0.7, unconfirmed. See the v0.7 revision-log entry: `open-neris-app`'s real ambiguities got resolved during the planning interview, before `test-implement` ever started, rather than mid-implementation. If planning is reliably doing that job, a quiet `test-implement` guardrail might be a sign the process is working, not a sign the guardrail's trigger conditions are wrong or that every target so far has coincidentally lacked real ambiguity. Weigh both explanations against whichever target satisfies the v0.5 selection criteria next, rather than treating either as settled.

## Dogfeeding plan

### Run 1 — Shenny (complete)

Chosen because it already had mature test infrastructure and its own governing docs. Validated gap-closure sequencing and the three-tier discipline's core split. Findings folded into v0.1.

### Run 2 — django-realworld-example-app (complete, full cycle)

Chosen as an unfamiliar-stack, archived, thin-test-coverage counterpart to Shenny — official Django implementation of the RealWorld/Conduit spec, archived since 2022, 16 unresolved open issues, no test suite. **Planning phase** validated bootstrap sequencing for the first time, surfaced real pre-existing bugs (a missing object-level authorization check, a reference-equality bug that happens to work by coincidence), and surfaced a real runtime-viability gap (a pinned 2016-era Django release capping the usable Python version). Findings folded into v0.2. **Implementation phase** executed all six phases — 135 tests, one commit per phase, no stops — validated the phase-sizing floor, surfaced two more previously-unknown bugs (a duplicate-slug 500, an unreachable `/api/articles/feed` route shadowed by route ordering), corrected the CONTEXT.md-growth-pattern assumption, tightened the coverage sweep's route-level granularity, and confirmed CI needs to reuse the Runtime Viability Check's verified environment rather than reimplementing its own — caught only because the CI job initially used a native `actions/setup-python` step instead of the verified Docker container and failed once GitHub's runner image dropped that Python version. Findings folded into v0.3. PR merged to the fork's `master` on 2026-08-15.

### Run 3 — rails-realworld-example-app (complete, full cycle)

Chosen as a third, distinct-stack counterpart — official Rails implementation of the same RealWorld/Conduit spec, archived since 2022, `test/` directory confirmed to be 100% untouched `rails new` scaffold. **Planning phase** surfaced verification-environment decay as a distinct source of runtime friction (EOL base image, dead package mirrors) separate from the app's own dependency ceiling, plus the Docker-tag-drift finding. Findings folded into v0.4. **Implementation phase** — kickoff deliberately left one known bug's fix-vs-characterize disposition open rather than letting the plan pre-resolve it, specifically to test the guardrail. Seven phases, 115 tests, zero application code touched (verified). Six real bugs handled, five of them newly discovered during implementation and not predicted by planning — most significantly, a Devise session cookie silently overriding a different user's JWT after signup, this project's most severe finding to date. The engineered live decision was weighed genuinely and resolved without a stop; the guardrail did not fire on that decision or on any of the five new findings, including the severe one. Findings folded into v0.5, including a reframing of what the guardrail result actually means (see Open questions) and a new severity-flagging trigger.

### Run 4 — open-neris-app (planning + six phases complete; deferred-items follow-up in progress)

Chosen as this project's own actively-developed target, run manually against the process rather than through a packaged skill (none exists yet) — the first non-fork, non-published-spec target, and the motivating case named back in v0.5's greenfield open question, though it turned out to already have a full schema and a partial app rather than being truly greenfield, so the existing bootstrap-sequencing process applied largely as-is rather than needing the undesigned tests-as-spec mode. **Planning** surfaced a real business-logic layer with no external spec (`reviewStatus`'s department-review workflow) alongside a genuinely external one (NERIS field semantics) in the same app, and required resolving two live ambiguities during the interview itself rather than during implementation — a NERIS-CSV cross-check for `module-relevance.ts`'s baseline module set, and confirming a counter-bucketing quirk was intentional. **Implementation** ran six phases (301 fast-suite tests, 35 Testcontainers DB tests) under manual-review commit mode, ending in a bounded self-review phase per v0.6, and surfaced two real bugs (a `z.coerce.date()` null-to-epoch coercion gap, a missing optimistic-locking guard on `submitIncident`) characterized rather than fixed at the time, flagged prominently in both `TESTING.md` and a dedicated `TEST-PLAN.md` section — consistent with, though not directly confirming, the v0.5 severity-flagging trigger working as intended. **Deferred-items follow-up** (this revision) reactivated the plan into new numbered phases for the backlog items that were merely deferred (the two known bugs, now approved for a real fix) versus genuinely blocked (UI-stability-gated E2E/accessibility/visual/cross-browser work, feature-existence-gated AI/LLM grading work) — see `open-neris-app`'s own `TEST-PLAN.md` for the resulting phase list. Findings folded into v0.7.
